## 2. Security model (the central design constraint)

Assume every player can read DevTools, the Network tab, React state,
localStorage, and every Supabase response.

Therefore:

| Invariant | Enforcement |
|---|---|
| A player can read **only their own** hidden dice | RLS on the private dice table, keyed on `auth.uid()` |
| Dice are **generated by the server** | Dice values originate in Postgres/Edge Function; the client never submits dice |
| The client cannot decide outcomes | All resolution runs server-side; client receives results |
| The client cannot write game-critical fields | No direct `INSERT`/`UPDATE` grants on game tables; writes go through validated actions only |
| A player cannot act for another player | Every action re-derives the actor from `auth.uid()`, never from request body |
| Realtime never carries private dice | Private dice table excluded from the Realtime publication |

Hiding dice with CSS, React state, or client-side filtering is **explicitly
forbidden**. If hidden dice are reachable from the browser before a legitimate
reveal, the architecture is wrong.

---

## 3. Public vs private data

**PUBLIC** (readable by any member of the room):
player identities & display names, dice **counts**, current bid, bid semantics
(normal/Bull), round type & status, turn/bidder/resumption pointers, Farewell
locked face, public event log, dice **revealed** by a legitimate resolution.

**PRIVATE** (readable only by the owning player):
that player's hidden dice for the current round.

**SERVER-ONLY** (readable by nobody via the API):
un-revealed dice of *other* players, RNG internals.

This split is a **database-level** split (separate tables with separate RLS
policies), not an application-level convention.

## 4. Data model

**Both slices are implemented** (`supabase/migrations/`): `profiles`, `rooms`,
`room_members`, `games`, `game_players`, and now `rounds`, `player_dice`,
`dice_reveals` and `game_events`.

### Private dice

`player_dice` is a separate table rather than a column on `game_players`, and
that is the whole point: a public query about someone's dice **count** cannot
widen into their dice **values**, because the values are not there to select.

Its policy contains no membership term at all —

```sql
using (player_id = (select auth.uid()))
```

— because membership is not what grants it. Being in the room is why you can see
the bid; it is not a reason to see anyone's hand.

`player_dice` is **never** in the Realtime publication. Replication is a second
distribution channel, and a table that is safe under RLS is not automatically
safe when broadcast. The migration itself raises if it finds the table
published, and a test asserts the publication's exact contents rather than its
size — a count passes when one table is swapped for another.

`dice_reveals` is the only route from private to public, and it runs through the
server when a challenge resolves.

Both protections were checked by breaking them. Replacing the policy with the
plausible mistake — "room members can see dice" — fails the suite immediately,
as does adding `player_dice` to the publication.

Two decisions from slice 1 worth carrying forward:

- **Elimination is a generated column** (`is_eliminated = dice_count = 0`), so
  the drift PART 77 warns about is structurally impossible rather than merely
  policed by convention.
- **`game_players.dice_count` has no upper bound yet.** Burst Dudo grants a die
  and whether a player may exceed their starting count is unresolved (R-007);
  adding a ceiling now would be inventing a rule.

### Original table plan (PROPOSED — Phase 1)

| Table | Purpose | Read access |
|---|---|---|
| `profiles` | display name, avatar, linked to `auth.users` | room co-members |
| `rooms` | room, short join code, host, lifecycle status | members |
| `room_members` | membership, seat order, presence-independent | members |
| `games` | a game inside a room; status, winner, `version` | members |
| `game_players` | per-game player: seat, dice **count**, active/eliminated | members |
| `rounds` | round number, type (normal/farewell), locked face, status | members |
| `round_bids` / current bid columns on `rounds` | current active bid: quantity, face, `is_bull`, bidder | members |
| `player_dice` | **PRIVATE** — the actual dice for a player in a round | owner only |
| `dice_reveals` | dice made public by a legitimate resolution | members |
| `game_events` | append-only event log | members |

Conventions: UUID primary keys, foreign keys with explicit `on delete`,
`created_at`/`updated_at`, `CHECK` constraints for enums and dice ranges,
unique constraints (room code, seat per game, one dice row per player+round),
and a `version` integer on the authoritative game state row for optimistic
concurrency.

Dice-count consistency (`game_players.dice_count` must equal
`array_length(player_dice.dice)`) is maintained by making **every** transition
a single server-side transaction, plus a constraint/trigger check.

### Indexes (planned)
`rooms(code)` unique · `room_members(room_id, user_id)` unique ·
`game_players(game_id, seat)` unique · `rounds(game_id, round_number)` ·
`game_events(game_id, created_at)` · `player_dice(round_id, player_id)` unique.

## 5. Action API (PROPOSED — Phase 3)

The browser never writes game state directly. It submits an **action**; the
server authenticates, validates, transitions, logs, and returns safe data.

Planned actions: `CREATE_ROOM`, `JOIN_ROOM`, `LEAVE_ROOM`, `SET_READY`,
`START_GAME`, `START_ROUND`, `MAKE_BID`, `DECLARE_BULL`, `DUDO`, `BURST_BID`,
`BURST_DUDO`.

Every action validates, in order: authenticated identity → room membership →
game membership → player active & not eliminated → game status → round status
→ action permission (turn or valid Burst) → bid legality → round-type rules
(normal vs Farewell) → concurrency version. Failure returns a stable error
code (`NOT_YOUR_TURN`, `INVALID_BID`, `STALE_STATE`, `PLAYER_ELIMINATED`,
`GAME_COMPLETE`, `UNAUTHORIZED_ACTION`, …), never a raw database error.

**Where the rule engine executes — DECIDED (D-002):** a single TypeScript
engine in `src/game`, imported both by the Edge Function that holds authority
and by the client for UI hints only. The database performs a version-checked
atomic commit. One engine, one set of tests, no drift.

**Implemented today:** clients hold `SELECT` only. There is no client
`INSERT`/`UPDATE`/`DELETE` privilege on any game table, so even a future policy
mistake cannot authorise a write.

---

## 6. Concurrency (PROPOSED)

Burst permits out-of-turn actions, so *any* active player may act at *any*
moment. The system must prevent double bids, stale bids, duplicate die changes,
and split-brain round state.

Planned mechanism: a monotonically increasing `version` on the authoritative
game-state row. Every action carries the version it observed; the write is
`UPDATE … WHERE id = $1 AND version = $2`, and a zero-row result means
`STALE_STATE` — rejected safely, client refreshes. Combined with
`SELECT … FOR UPDATE` row locks inside a single transaction so that read,
validate, and write are atomic.

---

## 7. Authentication (DECIDED — D-003)

Supabase Auth with **anonymous sign-in** plus a chosen display name. Anonymous
users are real `auth.users` rows, so `auth.uid()` and every RLS policy behave
identically to a registered user.

Consequence already reflected in the schema: abandoned anonymous accounts will
need pruning, so `rooms.host_id` is `ON DELETE SET NULL` — deleting a stale
account must never be blocked by a room it once hosted.

---

## 8. Realtime (PROPOSED — Phase 4)

Supabase Realtime distributes public state changes: membership, presence,
bids, Bull, Dudo, Burst, reveals, die changes, elimination, Farewell
transitions, round changes, completion.

**The `player_dice` table must be excluded from the Realtime publication.**
Realtime replication respects RLS for authorized channels, but the safest
posture is that private dice never enter a broadcast path at all.

Presence is used for online/offline indication only — **never** as
authoritative game state.

---

## 9. Reconnection (PROPOSED)

Authoritative state lives in Supabase, never only in React memory. On refresh
or reconnect the client re-fetches full public state plus its own private
dice, then re-subscribes. A temporary disconnect must **not** eliminate a
player.

## 10. Frontend architecture (PROPOSED)

```
src/
  app/          routing, providers, layout
  features/
    auth/  lobby/  room/  game/
  game/         PURE domain engine — no React, no Supabase
    rules/      bid legality, transitions, resolution
    types/      shared game types
  lib/          supabase client, action client, error mapping
  hooks/        realtime subscriptions, queries
  components/   reusable UI
  styles/       design tokens
```

`src/game` is a **pure, dependency-free, unit-tested** module — implemented, 55
tests. It has no React, no Supabase, no randomness and no clock, so every rule is
a function of its inputs and can be exercised exhaustively.

Its public surface:

| Module | Responsibility |
|---|---|
| `types.ts` | `Face`, `ActiveBid`, `RoundState`, rejection codes |
| `counting.ts` | Wildcard counting, and its suspension during a Farewell Round |
| `bids.ts` | Bid legality, `ceil(n/2)` and `2n+1` transitions, face locking |
| `resolution.ts` | Dudo, Burst Dudo, correct Bull, elimination, Farewell trigger |
| `errors.ts` | `UnresolvedRuleError` |

A Bull is modelled as a declaration hanging off the current bid rather than a
bid of its own, because that is what it is: it re-reads an existing quantity as
"exactly" and introduces no quantity or face. A later bid replaces the whole
`ActiveBid`, which is how the Bull stops applying without any special handling.

**The engine is never given anybody's dice.** `resolveChallenge` takes each
player's dice *count* and the relevant *total* on the table — both public — and
nothing else. Counting happens where the dice already live, in Postgres, and
only the total travels.

This is not protection against a compromised server: anything holding the
service key can read `player_dice` directly. It is protection against the way
hidden information actually escapes — a log line, an error report, a crash
payload that happens to include the function's inputs. The engine cannot leak a
hand into any of those, because it was never handed one.

Tests still state scenarios as hands, which is the natural way to describe a
table. A test-only helper converts them, so what crosses into the engine in a
test is what crosses in reality: a count.

**Undefined rules raise.** Every branch the house rules leave open throws
`UnresolvedRuleError` carrying the rule id and the concrete situation. This is
deliberate: an engine that guesses would bake an invented rule into the product
and the guess would be invisible. The one exception is R-009, documented in
`GAME_RULES.md` §4, which needs a working default because every bid passes
through that check.

The UI reads state and dispatches actions; it is never the authority. Game rules
never live inside JSX.

## 10a. Database verification

`scripts/test-db.sh` spins up a throwaway PostgreSQL 16 cluster, applies a local
shim for the Supabase-specific objects the migrations depend on (`auth.uid()`,
the `anon`/`authenticated` roles, the `supabase_realtime` publication), applies
`supabase/migrations/` in order, and runs `supabase/tests/`.

Migrations are applied as **`app_owner`, a role with neither `SUPERUSER` nor
`BYPASSRLS`**. This is the point of the harness: a superuser bypasses RLS
unconditionally and would mask exactly the class of bug that matters here. It
already earned its keep — it is why `FORCE ROW LEVEL SECURITY` was removed
(it would have put the membership predicates back under the policies they exist
to evaluate, producing infinite policy recursion).
